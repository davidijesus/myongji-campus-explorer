## Automatic official menus

The native refresh client checks the approved Pages endpoint after loading its cache and when the app opens or resumes. Automatic requests are deduplicated and limited to one attempt per 15 minutes; pause cancels outstanding work. Manual refresh still requires the existing user-gesture bridge. Automatic behavior is restricted to the exact approved Pages URL; a custom configured endpoint retains manual-refresh behavior.

Responses are size-bounded and validated before replacing the atomic local cache. Older versions, same-version conflicting content, malformed responses and network failures retain the previous valid snapshot. Official records preserve Korean text, observation/check times and individual meal dates; they have `publishedAt: null` and `reviewedAt: null`, without fabricated translations. The UI recalculates expiry in Asia/Seoul and distinguishes automatic originals from human-reviewed summaries.

An existing APK with an empty endpoint needs one initial update containing this client and its URL. Later published menu snapshots do not require rebuilding the APK. **The client checks automatically, but scheduled university-source collection is not enabled.** Snapshots currently require an explicit collection/review/publication through the existing `gh-pages` branch. See [the feed contract and pending schedule](../docs/AUTOMATIC_MENUS.md) and [release verification](../docs/RELEASE_0.6.5.md). Installed Android validation remains outstanding.

## Build

Use the complete frontend source with PowerShell 7, Node 22, JDK 18, Android SDK platform 36 and build-tools 36.0.0. Run `npm ci` and `npm run build` from the project root to create `preview.html` and `build/core`. Review the resulting HTML and update both build-script SHA-256 pins only after approval.

Required source support files include `scripts/naver-fixtures.cjs`, all three JSON files in `docs/v055-validation/community-interop`, and this Android folder's source/tests/resources. Use an existing authorized development keystore outside the source tree; the script will not create or replace it.

```powershell
pwsh -NoProfile -File android-standalone/build.ps1 `
  -Sdk "$env:LOCALAPPDATA\Android\Sdk" `
  -Jdk 'C:\Program Files\Java\jdk-18.0.2.1' `
  -BuildRoot 'C:\Builds\myongji-065-reviewed' `
  -Keystore 'C:\Signing\existing-development.p12' `
  -OutputApk 'C:\Builds\myongji-campus-explorer-v0.6.5-development.apk'
```

Choose a fresh build directory. Omitting `CommunityEndpoint` now uses the approved Pages feed; explicitly pass an empty value to prepare an offline-only build. Neither option changes WebView networking or location permissions. The optional Gradle publisher path uses the same resource graph, HTML pin and feed default, but requires the maintainer's publisher identity and signing environment. No Gradle publisher build is claimed here.

## Circular icon resource contract

`mobile/assets/icon.png` is the approved 1024x1024 RGBA circle with transparent pixels outside its blue artwork. Packaging copies its bytes unchanged to `drawable-nodpi/ic_launcher_art.png` before SDK resource processing.

Default `mipmap/ic_launcher` and `mipmap/ic_launcher_round` aliases point to that artwork. API 24/25 and round-icon consumers receive the transparent legacy PNG. Only normal `ic_launcher` has a `mipmap-anydpi-v26` adaptive override. An explicit non-adaptive API 26 bitmap resource keeps `roundIcon` on the transparent PNG; otherwise AAPT2 can automatically generate a round alias to the adaptive icon. The adaptive foreground uses proportional 21/108 insets on each side, leaving the artwork within the central 66/108 safe circle, over an opaque pale `#F4F7FB` background. The PNG is not painted onto a new blue square.

The adaptive background is intentionally opaque: Android's AdaptiveIconDrawable initializes its internal bitmap with black, so a transparent background can reveal black inside the mask. Its outer silhouette and launcher normalization remain system-controlled. We do not promise a circular outer contour or transparent adaptive corners on every device; supported round-icon consumers use the separate circular legacy resource.

References: [Android adaptive-icon guidance](https://developer.android.com/develop/ui/compose/system/icon_design_adaptive), [Android 16 AdaptiveIconDrawable source](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-16.0.0_r1/graphics/java/android/graphics/drawable/AdaptiveIconDrawable.java), and [Android 8 implementation](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-8.0.0_r1/graphics/java/android/graphics/drawable/AdaptiveIconDrawable.java).

## Runtime and verification limits

The native wrapper still serves reviewed local HTML at `https://appassets.androidplatform.net/assets/index.html`. WebView networking and arbitrary embedded remote resources remain blocked. The permission set remains INTERNET plus optional foreground COARSE/FINE location; no background permission or service is added. The dedicated native client performs menu requests. Favorites/preferences, Naver navigation and the manual bridge's gesture checks are preserved.

The direct builder executes native JVM policies, signs with the existing development identity, verifies SDK metadata/signature/alignment and exact HTML, and rejects unexpected `.so` libraries. Desktop browser/CSP tests and host JVM tests are separate from Android runtime tests. No device installation, emulator execution, store publication or new signing key is claimed for this change.
